# 実装と変更

実装前に[文書の責務と更新](../guidelines/documents.md)、[作業原則](README.md)、対象Product・Requirements・Designを読みます。
Requirementsがなければ[要件の作成](requirements.md)、対応するDesignがなければ[設計の作成](design.md)を先に行います。

## 変更を進める

既存構成と依頼から変更の種類を判断し、ガイドラインの「変更の扱い」に従って文書と実装を更新します。
要件に矛盾があれば実装で補わず、Requirementsと対応するDesignを直します。
実装中に設計の不備を見つけた場合は、実装と合わせてDesignを修正します。

実装後の実装方法だけの改善では、振る舞いや制約も変わらないかを確かめてから進めます。
要件に影響するなら要件変更として扱います。
詳細な変更理由と確認結果は変更記録やGitの履歴へ残します。

## 検証する

Requirementsの各シナリオに対して、何を確認すればThenを観測できるかを決め、実際に確認します。
正常系だけでなく、失敗・境界の条件も扱います。
結果は条件ごとに、確認できたこと・失敗したこと・未確認のことを分けます。
テストコードが必要な変更では適切なテストを実行し、文書の機能なら実際の読み取りとリンクの確認で確かめます。

文書の検証では、リンク先の存在、RequirementsとDesignの一対一の対応、親Productの参照、テンプレートの固定見出しを確認します。
URLは実在と内容を確認します。
入口から必要なガイドライン・テンプレート・手順へたどれるか、特定の環境のパスや外部の未配置文書に依存していないかも確認します。

検証結果は要件やDesignに書き足さず、変更記録または確認記録として保存します。
完了報告では、作成・変更したもの、実際の確認結果、残る判断を短く伝えます。
