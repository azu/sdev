# 仕様を読み、関連する箇所を調べる

[English](review.md)

RequirementsとDesignを読みながら、もう一方の文書の関連箇所をJevで調べます。
コード差分については、要求や設計の対応先が見つからない箇所を別の操作で確認します。
結果は人が調べるための材料とし、仕様の正しさや変更の違反を確定したとは扱いません。

Agentは[文書の責務](documents.ja.md)と[実装と検証](agent.ja.md#実装と検証)に従い、通常どおりRequirements・Design・実装を変更します。
`review.json`へのリンク・理由・具体例の手書きは、必要なときに加える任意の材料です。

## レビューを起動する

対象Product・Requirements・Designと実際の変更を読みます。
合意した比較対象を使い、プロジェクトのGitルートで起動します。

```sh
sdev review --serve --jev
```

起動前に、サーバーの環境変数`JEV_API_KEY`を設定します。
サーバーは[TypeSafe公式API](https://api.typesafe.ai/openapi.json)を使い、キーをHTMLやブラウザー側のコードへ渡しません。
仕様本文やコード差分の外部送信は、`--jev`を明示的に有効にした場合だけ行います。

コマンドが表示した`127.0.0.1`のURLを開き、終了するときはCtrl-Cを押します。
比較対象の指定がなければ、HEADと作業ツリーを比較し、ステージ済み・未ステージ・無視対象ではない未追跡の変更を含めます。

比較元は`--base REF`、追加する仕様は`--spec PATH`、ディスクキャッシュの保存先は`--cache-dir PATH`で指定します。

```sh
sdev review --serve --jev --base main --spec docs/feature/requirements.md --cache-dir "$HOME/.cache/sdev/review"
```

仕様のパスは例です。
実在するRequirementsやDesignを指定します。
起動前にAgentがレビュー項目を作る必要はありません。

## 文章を読み、関連する仕様へ進む

左側の目次で現在の節を確認し、見出しを選んで本文へ移動します。
ファイルの切り替えは文書上部の選択欄を使います。

Requirementsの文章をクリックすると、関連するDesignの一節を表示します。
Designでは、その方法が支える操作・結果・制約をRequirementsから探します。
読む箇所は文単位のまま、関連先は方法や条件を確認できる段落やリスト項目として表示します。
参照先の太字の見出しの下に段落を示し、その中で最も直接対応する文を特定できれば強調します。
強調がない場合も段落は読め、強調の取得だけが失敗した場合は再試行できます。
表は行単位で選び、列見出しと値の関係を保って照会します。
関連先の表も行・列の形で読み、対応する行を特定できれば強調します。行へのコメントは表の後で確認できます。
技術名の一致は求めず、選んだ文の意味を見出しや周囲の段落で補います。
理由や具体例を生成するのではなく、実際に取り込んだ文書の一節を返します。
J/Kで次や前の文へ進むと、読んでいる箇所の関連表示も更新します。

ホバーやTabでフォーカスを移すだけでは、詳細を開いたり切り替えたりしません。
クリックでは文章へフォーカスし、詳細を開いたままにします。
Escまたは外側のクリックで詳細を閉じます。
文章にフォーカスした状態でEnterを押すかJ/K以外の文字を入力すると、その直下でコメントを書き始めます。
入力欄の中では通常どおり文章を編集できます。

返された一節を、読んでいる文章と照らして判断します。
候補があることは、設計が要求を満たす証明にはなりません。
同じ単語や要求の言い換えだけでなく、選んだ要求を実現する方法や選択が書かれているかを読みます。
不確かな関連候補は表示しません。
調べた範囲で明確な対応が見つからなくても、対応する設計が存在しないとは断定しません。
候補範囲の制限、本文の取得不能、照会の失敗は表示し、架空の参照で埋めません。

関連先があっても、判断に使える設計上の選択が書かれているとは限りません。
要求の言い換えにとどまる場合は、そのDesignの文にフォーカスし、足りない決定と、それがないため判断できないことをインラインコメントに残します。
たとえば「文の区切り方が不明で、日本語や同じ行に複数文がある場合の選択単位を判断できない」と書きます。
不足の指摘と実装方法の提案を分け、対応があるように見せるための方法を創作しません。

## 仕様の対応先が見つからないコード変更を確かめる

仕様がコード変更を扱っているか調べたいときは、画面の追加操作でコード差分を検査します。
各変更箇所に対応するRequirementsやDesignがあるかを判定し、対応先なしや不確かな候補について実際のDiffを開きます。

開始前に、入力として表示される変更ファイルと仕様ファイルを確認します。
実行中は照合しているファイルと検査済み件数を確認します。
候補ごとに「仕様に残す変更か」「記載があるか」の判定を分けて読み、実際の差分を調べます。
停止や失敗は未完了として扱い、続きから再開します。

変更する条件と振る舞いを読んでから、何を直すか判断します。
未記録の利用者向けの規則はRequirements、実現方法を理解するために必要な重要な選択はDesignで扱います。
通常の補助関数などの実装詳細は、対応する仕様が見つからないことだけで違反にしません。

調べた内容と、候補を探した範囲の限界を示します。
未検証のコード、取得できない本文、限られた探索範囲を、仕様の不足が確定した結果として報告しません。
人の判断が必要な点を問いとして返し、依頼された範囲で対象文書や実装を更新します。

## 同じ入力の判定を再利用する

同じ判定にはメモリーとディスクのキャッシュを使います。
キャッシュキーには、実際の入力本文・差分・候補・モデル・判定条件を含めます。
それらが一致するときだけ再利用し、変更があれば以前の判定を失効させます。
キャッシュされた結果にも、元の判定と同じ調査範囲と限界があります。

作業ツリーの配信では、仕様やコードを保存すると本文・差分・判定の入力を自動更新します。
入力中のコメントはフォーカスが外れてから反映し、対象の文章が変わったコメントは更新前の指摘として保持します。
自動更新の状態と取得時刻を確認し、切断や失敗があれば以前の本文を読んでいると判断します。
`--input`や`--head`、単一HTMLは固定した比較のため、変更後のレビューには新しい取り込みを使います。
以前の結果を、新しい文章や差分の確認済みの印として扱い直しません。

## コメントを持ち帰り、必要なら比較を固定する

コメントはページ内で保持し、コピー・保存・サーバーへの受け渡し後も残します。
「メモをコピー」で対象の文章や問い・比較対象・コメントをMarkdownとしてコピーし、Agentとの会話へ貼り付けます。
サーバーモードの「Agentに渡す」は、起動元の実行出力へ同じ情報を返します。
起動したAgentは、実行中のコマンドから`review.feedback`のJSON行を読み、元の引用と比較対象を確かめて対応します。
画面の受領表示は、Agentが読んだことや修正済みであることを示しません。

Agentは指摘に対応する文書や実装を修正して検証し、サーバーが新しい版を取り込んだことを確認してから解決を返します。
`review.feedback`に含まれる`notes[].id`を指定し、確認した修正内容を`summary`へ書きます。本文を変えただけ、または要望を満たすか未確認の指摘は解決済みにしません。
起動時に表示されたURLを`SDEV_REVIEW_URL`、コメントIDを`SDEV_COMMENT_ID`、確認した内容を`SDEV_RESOLUTION`に設定して、次のように返せます。

```python
import json
import os
import urllib.request

origin = os.environ["SDEV_REVIEW_URL"].rstrip("/")

def post(path, value):
    request = urllib.request.Request(
        origin + path, data=json.dumps(value).encode(),
        headers={"Origin": origin, "Content-Type": "application/json"},
    )
    with urllib.request.urlopen(request) as response:
        return json.load(response)

current = post("/api/refresh", {"revision": ""})
print(post("/api/feedback/resolve", {
    "id": os.environ["SDEV_COMMENT_ID"],
    "revision": current["revision"],
    "summary": os.environ["SDEV_RESOLUTION"],
}))
```

`revision`を取得した後にレビュー対象が変わると、解決は拒否されます。変更後の版を確認し直してから再送します。
解決状態は開いたページへ自動反映され、元の引用と確認した版は残ります。サーバーの終了後も必要な記録はコピーか書き出しで保存します。
保存にはMarkdownかJSONの書き出しを使い、入力中の下書きは先にコメントとして追加します。
調べた内容・実行した確認・未確認の操作を分けて報告します。
DOMテストの成功を、実ブラウザーの使いやすさや意味の正しさの確認とは扱いません。

比較を固定したい場合や、Agentの追加材料が必要な場合には、入力の準備と単一HTMLの生成も使えます。

```sh
sdev review --prepare --output /tmp/review.json
sdev review --input /tmp/review.json --output /tmp/review.html
```

この手順は任意です。
材料を加えるときは`title`と`items`だけを編集し、取り込んだ本文と版を保持して、根拠のある参照を使います。
記録された理由・推定・理由不明と、実行して観測・説明用・未確認の例を区別します。
オフラインのHTMLでは、取り込み済みの材料とコメントを扱えますが、Jevへのその場での照会はできません。
その照会には`--jev`を有効にしたサーバーを使います。
