# 既存コードのあるプロジェクトで仕様を起点にした開発を始める

[English](brownfield.md)

すでにコードがあり、Product・Requirements・Designがないプロジェクトで、次の機能変更や新しい機能の作成を仕様から始められるようにする手順です。
[文書の責務と更新](documents.ja.md)と[エージェントの作業原則](agent.ja.md)を読みます。
コード全体の仕様は作らず、始めるために必要な文書だけを書きます。

## 適用する場面を確かめる

Productと機能の一覧があり、変更が触れる機能のRequirementsとDesignも書かれている場合は、この手順を繰り返しません。
[文書の責務と更新](documents.ja.md#変更の扱い)に従って、既存の文書を変更します。

Productと機能の一覧があり、変更が触れる機能の仕様だけがない場合は、[触れる機能を選ぶ](#触れる機能を選ぶ)から進めます。
既存機能を変えない新しい機能を作る場合は、既存機能の現状を書き起こしません。
[Requirementsのガイド](requirements.ja.md)に従って新しい機能のRequirementsを作り、Productの機能の一覧へ行を足します。

次の状態になったら、始める手順は完了です。
必要のない文書は、完了のために書き足しません。

| 始めたい作業 | 必要な文書 |
| --- | --- |
| 既存機能の変更 | 親Productと、変更が触れる機能のRequirementsとDesign |
| 新しい機能の作成 | 親Productと機能の一覧 |

## 読み取ることと質問すること

今の振る舞いと構成（何をしているか）は、コードとテストで確かめます。
READMEや既存文書の振る舞いの説明は、コードのどこを読むかの手がかりにし、コードとテストで確かめてから書きます。
コードとテストで確かめられる内容を開発者へ質問しません。

理由（なぜそうしているか）は、コードからは分からないことがあります。
READMEや既存文書、履歴に理由の説明があっても、それは書いた時点の説明であり、今も正しいとは限りません。
資料にある理由は候補として扱い、開発者が今も正しいと答えるまで確定しません。

開発者へ質問するのは、確定していない理由と、資料どうしの食い違いです。
理由の質問は、次の機能変更や新しい機能の作成を始めるために必要なものに限ります。
始めるために必要のない理由は、不明のまま残します。

理由を質問するときは、資料から考えられる候補を選択肢として示せます。
候補は質問の材料です。
開発者が選ぶか自分の言葉で答えるまで、文書へ理由として書きません。
質問の進め方は[質問で考えを具体化する](agent.ja.md#質問で考えを具体化する)に従います。

質問は、文書を書いて保存する前に会話で行います。
文書のレビューを、理由を確認する最初の場にしません。
開発者がすぐに答えられない項目だけを、[確定と未確認を書き分ける](#確定と未確認を書き分ける)に従って未確認として残します。

既存文書の説明とコードの振る舞いが食い違う場合は、両方を開発者へ示し、どちらが意図した振る舞いかを確認します。
既存文書にだけあり、コードとテストで確かめられない振る舞いも、食い違いと同じく扱います。
返答を受けるまで、どちらか一方を現状として確定しません。

## 確定と未確認を書き分ける

文書の本文には、確定した内容だけを書きます。
確定した内容とは、コードやテストで確かめた振る舞いと構成、開発者が答えたか今も正しいと確認した理由です。

確定した内容は、プロダクトや機能そのものの説明として書きます。
「READMEは…と説明している」「コードでは…となっている」のように、資料が何を言っているかの形で書きません。
どの資料で確かめたかは、文書を提示するときの[根拠の内訳](#現状を提示する)に書きます。

開発者の確認を待っている内容は、本文に書かず、その文書の未決事項に未確認として書きます。
未確認の項目には、確認したいこと、資料から読み取った候補とその資料、決まるまでは本文に書かないこと、判断する人を書きます。
開発者が確認したら、確認した内容を本文へ書き、未決事項から項目を消します。

開発者も知らない理由は、確定も確認待ちもできません。そのような理由は、本文に不明と書きます。
書き方は[現状を書き起こす](#現状を書き起こす)に従います。

## 材料を確認する

READMEと既存文書、テスト、パッケージやディレクトリの構成、開発者が説明する次の変更を確認します。
履歴やIssueは、理由を確かめる必要がある箇所に絞って読みます。
材料として読んだ非公開の情報や認証情報、発言者の名前や連絡先は、文書へ写しません。

## Productを書き起こす

[Productのガイド](product.ja.md)と[Productテンプレート](../templates/product.ja.md)に従ってProductを作ります。
Productは最初の1回だけ作成します。

目的と利用場面は、なぜ作ったか、誰がどの場面で使うかを表します。
READMEなどに動機や方針の説明がある場合は、読み取った内容を開発者へ示し、今も正しいかを確認してから書きます。
既存の説明を、確認なしに現在の目的として確定しません。
資料から分からない利用者や提供価値は開発者へ質問し、返答を受けるまで仮定で埋めません。
確認を待つ項目は、[確定と未確認を書き分ける](#確定と未確認を書き分ける)に従ってProductの未決事項に書きます。

主要な概念と機能の一覧は、今あるものを表します。
コードと既存文書から読み取り、読み取った内容を開発者へ示して確認します。

主要な概念には、利用者にも見える概念の名前と意味を書きます。
名前はコードや既存文書ですでに使われているものを使い、書き起こしのために新しい名前を作りません。
内部だけで使う型や関数の名前は含めません。
同じ概念に別の名前が使われている場合は、両方を開発者へ示し、どちらを基準にするかを確認します。

機能の一覧には、機能の名前、1行の説明、仕様を書きます。
機能は利用者が名前で呼べる振る舞いのまとまりとし、パッケージやディレクトリの名前をそのまま機能にしません。
仕様の列には、Requirementsがある機能ではそのRequirementsへのリンクを、ない機能では「未作成」と書きます。
この段階では、機能ごとのRequirementsとDesignを作りません。

```markdown
| 機能 | 説明 | 仕様 |
| --- | --- | --- |
| 設定ファイルの読み込み | 設定ファイルを探して検証し、検査の条件を決める | [Requirements](features/config-loading/requirements.md) |
| 結果の出力 | 検査の結果を選んだ形式で表示する | 未作成 |
```

振る舞いの細部、受け入れ条件、コードの場所、機能どうしの依存は一覧に書きません。
一覧にない機能が後から見つかった場合は、一覧へ追加します。
一覧が大きく読みにくい場合の分け方は、プロジェクトが選びます。
Productを分けることも、一覧を別の文書に分けてProductからリンクすることもできます。
どちらの場合も、Productから機能の一覧へたどれる状態を保ちます。

## 触れる機能を選ぶ

開発者が説明する次の変更をもとに、機能の一覧から書き起こす範囲を決めます。
変更が触れる機能、触れない機能、判断できない機能を分けて開発者へ示し、開発者が範囲を直せるようにします。

一覧の説明だけでは判断できない機能は、判断できないものとして示します。
コードを確認した結果か開発者の返答で決まるまで、触れない機能として扱いません。
触れない機能は、機能の一覧に載せるだけにします。

## 現状を書き起こす

選ばれた機能だけ、[Requirementsのガイド](requirements.ja.md)と[Designのガイド](design.ja.md)に従ってRequirementsとDesignを作ります。
現状を表す文書のための専用のテンプレートや文書の種別はありません。
通常のRequirementsとDesignとして書き、機能の一覧の仕様の列をリンクへ書き換えます。

現状の文書には、今の振る舞いと構成だけを書きます。
今回行いたい変更の内容は含めません。
機能の一部だけを書き起こした場合は、Requirementsのスコープ外に、まだ書き起こしていない振る舞いがあることとその範囲を書きます。

Designの構成と処理の流れは、コードとテストで確かめて書きます。
READMEや既存文書にある設計の説明を、コードで確かめずにDesignへ写しません。

開発者に質問しても理由が分からなかった箇所は、Designの判断理由を書く位置に、理由が不明であることを文章で書きます。
検討した代替手段も、記録がなければ、記録がないことを書きます。
「現状の記述なので、なし」のように、代替手段を検討しなかったと読める書き方をしません。
推測した理由は書きません。

不明な理由が次の変更の判断に必要な場合は、開発者へ質問します。
開発者にも分からない場合は不明のまま残し、変更の理由は今回の判断として新しく書きます。

## 現状を提示する

文書を開発者へ提示するときは、根拠の内訳を次の4つに分けて報告します。

- コードやテストで確かめた内容
- 開発者の返答や確認による内容（既存文書の説明を開発者が今も正しいと確認したものを含む）
- 未確認として未決事項に残した内容
- 不明のまま残した内容

内訳は会話やPR本文に残し、文書には保存しません。
文書には、未決事項の未確認の項目と、本文の不明だけが残ります。

未確認の項目が残っている場合は、提示するときにその項目を開発者へ質問します。

## 変更を書く

開発者が現状の文書を確認した後に、次の変更を、その文書の更新として書きます。
次の変更の判断に必要な未確認の項目が残っている場合は、先に開発者へ確認します。
確認を受けるまで、現状と変更を同じ更新に混ぜて確定しません。
現状と変更を分けることで、Gitの差分から変更前後の振る舞いの違いを読めます。

ここからは、仕様のあるプロジェクトと同じ進め方です。
[文書の責務と更新](documents.ja.md#変更の扱い)と[依頼の範囲とレビュー](agent.ja.md#依頼の範囲とレビュー)に従います。
2回目以降の変更では、機能の一覧から触れる機能を選び、仕様を書いていない機能だけ現状を書き起こします。
