# Designを書く

[English](design.md)

[文書の責務と更新](documents.ja.md)、[エージェントの作業原則](agent.ja.md)、[Designテンプレート](../templates/design.ja.md)を読みます。
親Productと対象Requirementsを特定して読み、不足する上位文書があれば先に作成します。
既存Designがあるなら、実装中の改善か、要件変更か、実装後の実装方法だけの改善かを調べ、更新方針を選びます。
依頼やコードから判断できない場合だけ確認します。
テンプレートは[選び方](documents.ja.md#テンプレートの選び方)に従って選び、上のリンクは適用するものがない場合のsdevの既定テンプレートとして使います。

## 既存構成と設計の論点を調べる

[質問で考えを具体化する](agent.ja.md#質問で考えを具体化する)手順に従い、調査で確認できる技術的な事実と、利用者に聞く制約や判断を分けます。
代替案の選択で利用者の期待や運用が変わる場合は、違いと根拠付きのおすすめを質問ツールで示し、回答を踏まえて次の論点を掘り下げます。
任された技術選定を一つずつ利用者に決めさせず、既存規約と調査で決められる実現方法は理由を添えて具体化します。

コードや文書の既存構成、関連する規約、影響する処理やデータ、類似の実装を確認します。
継続的な開発規約を確認し、不足する利用条件はRequirements、共通の規約はガイドラインへ整理します。
Designからのリンクは[文書の参照方向](documents.ja.md#文書の参照方向)に従い、別のDesignや実装ファイルへは付けません。
この規則は、調査のために既存文書やコードを読むことを妨げるものではありません。
既存構成への影響がない場合も、その理由を確認します。

成果物の形と責務、処理の流れと失敗時の扱い、データの型・構造・関係、公開する接点を決めます。
外部依存の接続・認証・障害時の扱い、取得・利用・保存・削除・保護、権限の境界を具体化します。
性能・規模・運用上の条件がある場合は、RequirementsやProductの目標に合う方法を選びます。
通常と異なる公開・移行・復旧が必要か、互換性や技術上の制約は何かも確認します。

自明でない判断は代替案を比較し、単純さと既存規約を基準に選定理由を示します。
技術の前提は必要に応じて一次資料で確認します。
契約・費用・利用上の制約を新しく決める必要が生じた場合は、Requirementsの不足として利用者に確認します。
Designだけで要件を変えません。

## 執筆する

新規文書は選んだテンプレートと利用先の配置規約に従って保存します。
指定がない場合は、対応するRequirementsと同じ機能ディレクトリに`design.md`を置きます。
冒頭でRequirementsとProductへリンクし、実現する仕組みの全体像と主要な流れを示します。

全体像を具体化する順に、各部分の責務、処理、データ、接点を説明します。
API名・型名・数値を出す前に、その仕組みの役割と目的を示します。
利用者の操作、内部処理、画面表示など、対象や細かさが変わる箇所を小見出しと段落で分けます。
各段落は[共通の書き方](documents.ja.md#説明を組み立てる)に従い、要点から説明を展開します。

主に説明する場所を決め、ほかの節では必要な要点と参照にとどめます。
細かな内部ファイル構成は配置規約へ、機能をまたぐ設計は別の文書へ整理します。

テンプレートの各欄は、対象に合わせて次のように書きます。

- 図: 構成ややり取りを文章だけで追いにくい場合に使い、不要な項目には理由を書く。
- 接点: 型やAPIが不要な文書の機能なら、実際に読む文書とリンクを説明する。
- デプロイ: 通常の反映手順で足りる場合は特記事項を「なし」とする。

### 説明をつなげる例

一覧をCSVへ保存し、その結果を利用者へ知らせる架空の機能を例にします。
次の説明では、処理と表示の関係が途切れています。

```text
export()でCSVを作る。通知を出す。保存先のパスを返す。
```

役割を先に示し、処理の結果がどう使われるかをつなげます。

```text
利用者が一覧をファイルに保存できるよう、出力操作からexport()を呼び出します。
export()は一覧をCSVへ変換して保存し、保存先のパスを返します。

保存が成功したら、そのパスを完了通知に表示します。
```

見出しで分類するだけでなく、保存処理が返すパスを通知に使うという文同士の関係を説明しています。

## 読み返す

まずRequirementsと照らし合わせ、条件を決め直さずに実装できる情報があるかを確認します。
データ要件が保存・削除・保護の方法につながるか、例外時の流れと選定理由が明確かを読みます。
実装を妨げる未決の技術判断があれば解消します。

次に先頭から読み、全体像から詳細へ進めるか、見出しから説明対象が分かるかを確認します。
見出しで分類できていても、段落内が情報の羅列なら直します。
各文が前の文の何を受けるか、役割を説明する前にAPI名や数値を出していないかを確かめます。
同じ説明の繰り返しや粒度の混在は、[変更の扱い](documents.ja.md#変更の扱い)に従って配置や文章を見直します。

保存内容とリンク先を確認し、文書と要点を提示します。
機械的な検査と読み返しの判断は[確認手順](agent.ja.md#書いた後に確認する)に従って分けて報告します。
Designの作成・変更だけの依頼なら、レビューを依頼するところで作業を区切ります。
実装まで任されている場合や、利用者の判断が必要な場合は[依頼の範囲とレビュー](agent.ja.md#依頼の範囲とレビュー)に従い、実装へ進む際はRequirementsと合わせて入力にします。
