# Designを書く

[文書の責務と更新](documents.md)、[エージェントの作業原則](agent.md)、[Designテンプレート](../templates/design.md)を読みます。
親Productと対象Requirementsを特定して読み、不足する上位文書があれば先に作成します。
既存Designがあるなら、実装中の改善か、要件変更か、実装後の実装方法だけの改善かを調べ、更新方針を選びます。
依頼やコードから判断できない場合だけ確認します。
テンプレートは[選び方](documents.md#テンプレートの選び方)に従って選び、上のリンクは適用するものがない場合のsdevの既定テンプレートとして使います。

## 既存構成と設計の論点を調べる

コードや文書の既存構成、関連する規約、影響する処理やデータ、類似の実装を確認します。
継続的な開発規約を確認し、不足する利用条件はRequirements、共通の規約はガイドラインへ整理します。
Designからのリンクは[文書の参照方向](documents.md#文書の参照方向)に従い、別のDesignや実装ファイルへは付けません。
この規則は、調査のために既存文書やコードを読むことを妨げるものではありません。
既存構成への影響がない場合も、その理由を確認します。

成果物の形と責務、処理の流れと失敗時の扱い、データの型・構造・関係、公開する接点を決めます。
外部依存の接続・認証・障害時の扱い、取得・利用・保存・削除・保護、権限の境界を具体化します。
性能・規模・運用上の条件がある場合は、RequirementsやProductの目標に合う方法を選びます。
通常と異なる公開・移行・復旧が必要か、互換性や技術上の制約は何かも確認します。

自明でない判断は代替案を比較し、単純さと既存規約を基準に選定理由を示します。
技術の前提は必要に応じて一次資料で確認します。
契約・費用・利用上の制約を新しく決める必要が生じた場合は、Requirementsの不足として利用者に確認します。
Designだけで要件を変えません。

## 執筆する

新規文書は選んだテンプレートと利用先の配置規約に従って保存します。
指定がない場合は、対応するRequirementsと同じ機能ディレクトリに`design.md`を置きます。
冒頭でRequirementsとProductへリンクし、要件の本文は繰り返しません。
成果物と責務、処理の流れ、データ構造、接点、データの取り扱いを実装できる具体性で書きます。
型やAPIが不要な文書の機能なら、実際に読み取る文書とリンクを接点として説明します。

テンプレートに沿って図の必要性を判断し、不要な場合は理由を書きます。
細かな内部ファイル構成は配置規約へ委ね、機能をまたぐ設計は別の文書へ分けます。
通常の反映手順で足りる場合は、デプロイの特記事項を「なし」とします。
テストの設計と実行は[実装と検証のガイドライン](agent.md#実装と検証)に従って行います。

## 読み返す

ガイドラインで、Requirementsの条件を決め直していないか、実装に必要な情報があるかを確認します。
データ要件が保存・削除・保護の方法につながるか、例外時の流れが明確か、代替案の判断理由があるかを確認します。
未決の技術判断が実装を妨げる場合は解消します。
保存内容とリンク先を確認し、Requirementsと合わせて実装の入力にします。
