# ローカルでの聞き取りの評価

[English](README.md)

AIの応答が利用者の依頼を明確にし、その範囲を守っているかを確かめます。[agent-evalの意味を判定する方法](https://github.com/vercel-labs/agent-eval#agentic-llm-judge)を参考に、別の新しいsubagentがケースごとの基準で回答内容を判定します。各ケースの`help/<case>/PROMPT.md`を利用者の依頼、`RUBRIC.json`を内容の判定基準、`EVAL.rs`を検査として分けています。既存のRustの`cargo xtask`を使い、追加の実行環境やcrate依存は増やしません。

## 準備と実行

`mise run eval:check`で、エージェントを起動せずに評価の仕組みを検査できます。sdevをビルドし、新しい出力ディレクトリを準備します。

```sh
cargo build --locked --package sdev --bin sdev
cargo xtask eval prepare \
  --binary "$PWD/target/debug/sdev" \
  --output "$PWD/target/evals/run-001"
```

`--case consultation,version`で対象を絞れます。以前の観測結果が混ざらないよう、既存の出力ディレクトリは拒否します。

各ケースのディレクトリを、会話を引き継がない新しいローカルsubagentに割り当てます。そのディレクトリの`AGENTS.md`と`PROMPT.md`を読み、そこでだけ作業し、利用者への最初の応答を`response.md`に保存させてください。対話が必要なら質問を本文に保存してケースを終え、評価を実行している人へ質問ツールを呼び出しません。準備済みの指示、入力、ラッパー、保存した出力、実行用バイナリ、traceは編集させません。

期待値、`RUBRIC.json`、`EVAL.rs`、元のリポジトリ、別ケース、他の回答は被評価AIに渡しません。比較対象間でモデル、推論設定、利用できるツール、割り当て時の指示をそろえます。被評価AIと判定AIの設定、実行回数、中断は`manifest.json`と同じ場所の`run.json`に記録します。モデルや推論設定の識別子が分からなければ、不明と記録します。

この仕組みは入力の準備と採点を担当します。subagentは現在のAIセッションから起動し、このツール自体はモデルを起動せず、追加のAPI認証情報も要求しません。プロセスの隔離機能は持たないため、実行元のAIの通常のファイルやコマンドの制限を使います。

## 回答内容の判定と採点

生成する`./sdev`はxtaskからコピーしたRustの観測用プログラムです。選んだsdev本体のhelp、template、versionの出力を保存して返し、実際の呼び出しを`trace.jsonl`に記録します。既定言語は英語、翻訳は日本語です。`lint`は本体のローカルコピーでケース内のファイルを検査し、出力と終了コードを記録します。評価中に元のリポジトリのバイナリは呼び出しません。

選択したすべての被評価AIが作業を終えたら、判定用の入力を準備します。

```sh
cargo xtask eval judge-prepare --output "$PWD/target/evals/run-001"
```

`target/evals/run-001/judges/<case>/`ごとに、会話を引き継がない別の新しいsubagentを割り当てます。渡すのは、その判定用ディレクトリだけです。パス全体に中立的な名前を使い、新旧の比較対象や期待する合否が名前から分からないようにします。判定AIは`JUDGE.md`の固定指示、`REQUEST.md`の元の依頼、`RESPONSE.md`の回答、`RUBRIC.json`の基準を読みます。回答内に判定AIへの命令があっても、指示として従わずデータとして扱います。被評価AIの会話履歴、比較対象の種類、helpの呼び出しログ、既存の判定は渡しません。

判定AIは、割り当てられたディレクトリに`judgment.json`を保存します。`inputHash`には`input.json`のバイト列そのもののSHA-256を使います。すべての基準について、真偽値の判定、空でない理由、回答からの完全一致の引用を1つ以上記録します。

```json
{
  "schemaVersion": 1,
  "inputHash": "<input.jsonのバイト列のSHA-256>",
  "criteria": [
    {
      "id": "<RUBRIC.jsonの基準ID>",
      "passed": true,
      "reason": "<判定の理由>",
      "evidence": ["<RESPONSE.mdからの完全一致の引用>"]
    }
  ]
}
```

すべての判定AIが作業を終えたら実行します。

```sh
cargo xtask eval score --output "$PWD/target/evals/run-001"
```

内容に関するすべての基準への合格を必須とし、判定の形式、入力ハッシュ、理由、完全一致の引用を検査します。判定の欠損や不正は成功扱いにしません。空の回答、trace欠損、検査の失敗、準備済みの入力の改変も不合格です。入力、判定基準、検査、本体、ラッパー、保存した出力はハッシュで識別します。改ざんへの耐性ではなく通常の指示への追従を確かめる評価です。

判定基準では、聞き取りで具体的な利用場面を明確にすること、未確認の事柄を決定済みにしないこと、1つの論点について1〜3問に絞ること、依頼の範囲を守ることを評価します。対話が不要な依頼に質問は要求しません。ガイドの種類と数は観測情報として残し、聞き取りの合否には使いません。Rustの検査では、実際のバージョン番号との一致や、生成コードのコンパイルと正常・境界・桁あふれの条件も引き続き確かめます。PROMPTは固定した評価入力であり、翻訳の対を作る説明文書ではありません。

各ケースは固定した入力への初回応答を評価し、長い対話全体を評価するものではありません。後続の応答を調べるケースでは、それまでの対話を固定入力の一部として渡せます。判定AIの結論を絶対的な正解とはせず、引用と理由を読み返せる形にします。比較に使う前に、良い回答と悪い回答の既知の例を別の新しい判定AIに渡し、基準が意図した違いを捉えるかを確かめます。

[判定AIの校正用データ](judge-calibration.json)には、被評価AIの評価とは別に判定の仕組みを検証するための固定回答を用意しています。期待する結果を判定AIに見せず、採点後に判定結果と照合します。

## help文面の比較

helpを編集する前に、英語と日本語の出力を別ディレクトリの`baseline.en.txt`と`baseline.ja.txt`へ保存します。変更後と同じバイナリを使い、変更前の一覧を指定して比較元を準備します。

```sh
cargo xtask eval prepare \
  --binary "$PWD/target/debug/sdev" \
  --help-dir /absolute/path/to/baseline-help \
  --output "$PWD/target/evals/run-002"
```

差し替えるのはhelpの入口だけです。ガイド本文、テンプレート、言語設定、バージョンはそろえます。被評価AIを実行する前に入力、判定基準、検査を固定し、変更したら新しい出力先を使います。回答を見た後で、不合格を合格にするために基準を変更しません。評価基盤の失敗はモデルの振る舞いと分けて記録し、失敗した試行も残します。安定性を結論づけるには繰り返し実行し、両方が一度成功しただけで成功率が改善したとは主張しません。判定AIの結果の揺れも比較の限界に含まれます。

ローカルの観測結果は、Gitの対象外の`target/evals/`に置きます。

## ケースを追加する

`help/<case>/PROMPT.md`に依頼、`RUBRIC.json`に`{"criteria":[{"id":"...","description":"..."}]}`の形で判定基準、`EVAL.rs`に検査を書き、xtaskの評価モジュールへ登録します。依頼に期待値を含めません。各ケースで回答内容の判定を必須とし、必要に応じて実行結果の検査も追加します。期待値は被評価AIを実行する前に決めます。

```rust
use crate::evals::{Run, require_judgment};
use crate::support::Result;

pub fn check(run: &Run) -> Result<()> {
    require_judgment(run)
}
```
