# 仕様を中心にレビューする実験

[English](README.md)

実際の変更を一つ使い、コードの差分全体を読む前に、実装時の判断と具体的な結果から人が仕様を判断できるか試します。
任意のローカル実験であり、sdevの採用済みガイドや新しい製品コマンドではありません。
Requirements・Design・実装を同じブランチに置き、PRのスタックは前提にしません。
利用先の指示、Product・Requirements・Design、`sdev help workflow --lang ja`と`sdev help documents --lang ja`を先に読みます。

## 実際の変更を用意する

利用者と小さな変更を選び、実装前に、既存仕様と確認した意図から目的と観測できる受け入れ条件を特定します。
既存の条件と、明確化の提案を区別し、提案を利用者の決定に読み替えません。
基点のコミット、確認する仕様の版またはファイルのハッシュ、確認対象の実装を残します。未コミットのファイルも、基点のコミット名だけでなくハッシュで識別します。
ローカルの観測結果と実行ファイルのコピーはGit管理外の`target/spec-review/<run>/`へ、残す結果は会話やPR本文へ置き、`docs/`には追加しません。

意味のある選択をした時点で、採用した選択・短い理由・根拠となる仕様や規約を、会話やローカルの観測記録へ残します。
後からの説明は推定、理由が残っていないものは不明と明示します。既存コードでは調べた範囲を示し、元の実装者の意図を作りません。
通常の実装方法の選択には追加の承認を求めません。目的・範囲・利用者の振る舞いが未決なら確認し、その判断に依存する作業を待ちます。

## 仕様と結果を提示する

判断が必要な点を先に示し、代表例や根拠は別に読めるようにして、人が読む量を選べる形にします。
変更ファイルや関数だけでなく、仕様が扱う振る舞いや条件ごとにまとめます。
項目ごとに、対象の仕様、同じ入力に対する変更前後の結果、実装で補った判断、人に決めてほしい一点の順で示します。
変更前の動作、実装済みの変更案、未実装の追加提案を明示して分け、追加提案を変更案の観測結果へ混ぜません。
選んだ項目について、次を一組で示します。

| 項目 | 内容 |
| --- | --- |
| 仕様と目的 | Requirements・Designの該当箇所と、それが支えるProductの目的 |
| 具体的な結果 | 入出力、操作、画面など。実行して観測した結果と説明用の例を区別する |
| 実装で置いた判断 | 補った選択、記録した理由、根拠。推定や理由不明を区別する |
| 判断が必要な点 | 不一致、目的を満たさない例、根拠不明の判断。利用者への影響と不確かさを示し、指摘を作らない |
| 確認後の扱い | 人の判断、文書やコードの適切な更新先、影響する条件の再確認 |

このレビュー結果から仕様や必要なコード・差分へ案内し、RequirementsからDesignやコードへの逆向きのリンクは増やしません。
観測結果には仕様と実装の版を示し、変更後は影響する確認をやり直して、古い結果を新しい版の証拠にしません。
テストの成功と、仕様が目的を満たすかは別に報告します。

## レビュー方法を確かめる

既知のケースで、仕様との不一致と、仕様そのものの不足を分けられるか確認します。レビューを生成する前に期待する分類を固定します。
分類の確認用の例と、実際の変更の観測結果を分け、レビューする側が正解を見ていたかも記録します。
実際のlintの表示言語の変更に対して、次は説明用の確認ケースであり、sdevで観測した追加の不具合ではありません。

| 固定する入力 | 期待する区別 |
| --- | --- |
| 仕様は理由と使い方を日本語にすると定めているが、理由は英語 | 実装と仕様の不一致 |
| 仕様は理由を日本語にすることだけを定め、出力は`エラー`だけで直し方が分からない | 狭い条件には従えても、引数を直せるよう案内する目的を満たせない可能性がある。Requirementsを確認する |
| 理由と使い方が選択言語でそろい、有効な形式も分かる | 指摘を作らず、どう具体化されたかを説明する |
| 以前の理由文を英語にした経緯がコードから確認できない | 当時の理由は不明。意図的な方針や仕様の不具合の証明にはしない |

人は、要確認の点だけの表示と、代表例・判断理由を含む表示を比べます。
コードを読まずに判断できた箇所、コードを読む必要があった箇所と理由、役立った情報・負担だった情報、根拠のない指摘と見落としを残します。
小さな実験の定性的な反応であり、レビューの正確さや時間短縮を実証したとは扱いません。

## 判断から再確認まで進める

人はセッションのチャットで返答します。確認した振る舞いはRequirements、実現方法はDesignへ反映し、影響するコードと検証を更新します。
指摘ごとに人の判断と再確認まで追います。GitHubで行う場合は同じレビュースレッドを使い、対応を確認してからResolveします。投稿やResolveには、その環境で必要な許可を得ます。
後のAIの応答から指摘が消えただけでは解決としません。

実際の変更をレビューし、人の判断・必要な更新・再確認まで試し、表示の比較について人の反応を記録できたときに実験を完了とします。
反応がまだなら、そのことを明示します。テスト成功だけで実験完了とはしません。
効果を確認できなかった場合も条件と限界を残し、有効だった手順の既存ガイドへの反映は結果を確認してから検討します。
